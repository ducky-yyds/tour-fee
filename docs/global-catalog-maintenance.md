# 全球目的地覆盖与持续维护

本地完整数据库与原始资产是主版本。GitHub Pages 只是预览，不是全球目录或无损图片的唯一存储位置。维护入口为 `node scripts/maintain-local.mjs`；原件、数据库快照和迁移包流程见本地归档说明。

## 名录来源与覆盖含义

首轮于 2026-09-28 遍历以下公共目录，保留每个条目的原始页面、页号、语言、日期与 Wikidata 标识：

- [英语 Wikivoyage 城市条目](https://en.wikivoyage.org/wiki/Category:City_articles)：21,789 个条目。
- [中文 Wikivoyage 城市条目](https://zh.wikivoyage.org/wiki/Category:城市条目)：2,639 个条目。
- [Wikivoyage 条目等级说明](https://en.wikivoyage.org/wiki/Wikivoyage:Article_status)：Guide / Star 城市进入重点补齐队列。
- [Wikidata](https://www.wikidata.org/)：通过公开 API 补齐身份、别名、所属国家和实体类型；结构化数据使用 CC0，保留逐条来源。

首轮跨语言合并并对齐既有目录后，共 22,957 个已发现条目；首批500个身份查询进一步合并3个重复身份，当前为22,954个。这个数字包含需要确认范围的候选，**不是已经上架的城市数量，也不表示每个条目都是城市**。Wikivoyage 的城市模板也会用于岛屿、考古遗址和大型游乐园；仅仅出现在类别里不构成发布资格。

完整队列保存在 `data/destination-registry.json`，轻量报告保存在 `data/destination-coverage.json`。二者均不直接填充前端城市选择器。

- `available` / `published`：已有整理内容、在应用中可浏览的目的地。
- `goalReady`：这些已有目的地中，达到当前目标档位的数量。
- `publishedNeedsEnrichment`：仍可浏览，但要按重点城市新标准提升的目的地。
- `pending`：待确认范围、国家、中文内容、照片或门户归属的候选。
- `excluded`：有明确依据的机场节点等范围外条目，保留理由和交通参考。
- `globalCoverageComplete`：来源扫描完成，且全部候选已处理、已有目的地均达目标后才为 true。

2026-09-28 完成慕尼黑、香格里拉、汉堡、科隆和法兰克福批次及首批身份查询后：**190 个可用目的地，108 个达到目标档位，82 个已有重点城市待提升，22,764 个候选待处理**。在德国三城批次前为187可用、105达标；更早身份查询前曾为108达标、79待提升，更多别名成功对齐后识别出3座需要升档的既有重点城市，并无城市消失。国家及大洲分布始终统计全部可用目的地，升档不会把城市隐藏。以最近生成报告为准，后续批次会改变这些数字。

德国三城批次每城包含20处景点、5项独特体验、5种食物和5家住宿。105个条目及3张城市封面全部有本地真实照片；12家住宿配对应楼体或内庭，其余3家明确使用城市环境参考。照片授权与出处保留在媒体记录中；个别体验使用主题相关实景并明确说明，不代表某个活动场次或供应商套餐。景点门票之外的规划费用仍区分编辑估算与官网核验值。

## 内容门槛

| 档位 | 景点＋体验 | 其中独特体验 | 特色美食 | 住宿 |
|---|---:|---:|---:|---:|
| 新增普通城市、小镇 | 至少 10 | 至少 3 | 至少 5 | 至少 5 |
| 重点旅游城市 | 至少 25 | 至少 5 | 至少 5 | 至少 5 |
| 已有内容兼容底线 | 至少 20 | 至少 3 | 至少 5 | 至少 5 |

住宿、餐馆不计入 15 / 30 条核心内容目标。一个地点换名称、重复入口或同一食物的多家商户不能用来凑数。主题体验至少覆盖两类；远郊接驳、季节、预约和是否适合自动规划应明确记录。既有城市升为重点后，目标报告会列出差距；审计保留兼容底线，使有效的既有数据继续可用。`baselineCityIds` 防止已维护城市被意外删除。

每项需要中文说明、位置、推荐用时、来源和照片；预算区间明确标作编辑规划估算，不冒充实时房价、门票或商家菜单。未知价格不等于免费。日期未确认的节庆不会直接排入指定日期。

慕尼黑批次包含 20 个景点、5 个体验、5 个食物及5家酒店；香格里拉包含15个景点、10个体验、5个食物及5家酒店。城市 ID 分别为 `munich`、`shangri-la`；MUC / DIG 旧机场节点通过审核过的别名关联，仍保留旧旅行项目兼容。

## 发现、身份补全、整理与发布是不同阶段

```powershell
# 首次扫描 / 中断后继续：有时间预算，没有全局城市数量上限
py -3 scripts/discover-destinations.py --time-budget-seconds 1200

# 每周重新扫描来源；保留既有候选与整理状态
py -3 scripts/discover-destinations.py --refresh --time-budget-seconds 1200

# 每日继续身份、国家和城市范围判断；不会重复处理已成功实体
py -3 scripts/discover-destinations.py --identity-only --enrich-limit 500 --time-budget-seconds 900

# 导入已经整理的 source packs 后，仅更新覆盖报告，不访问网络
py -3 scripts/discover-destinations.py --offline
```

Linux 将 `py -3` 换为 `python3`。脚本使用已有 Python `requests` 依赖；可通过标准 `HTTPS_PROXY` 环境变量配置网络。本机代理不写入代码或提交到仓库。

每页和每批身份数据都会原子保存继续游标。出现超时、限流或来源错误时保留上次成功结果，不清空目录。`--enrich-limit` 是单轮资源预算；下一轮继续尚未完成的实体。缺失实体延迟重试，不不断占据队首。

身份类型未知、国家不明的条目保持待处理。岛屿、自然公园等进入“待关联门户城市”，不会被判定没有旅游价值；机场仅保留交通参考。候选中即使已确认是城市，也需要完成实际内容、费用口径与照片审核，才写入正式扩充包。

**目前没有后台中文内容生成服务，也没有把公开目录直接改写成成千上万篇城市介绍。** 自动任务负责名录发现、结构化身份核对、进度与缺项维护、已有采集器支持的数据刷新，以及审核后内容的归档和发布。需要文化判断、事实交叉核对和照片主题确认的内容必须继续逐批整理，不能把发现记录记作完成，也不能伪造商户、体验或价格。

后续官方旅游目录适配器应保存来源快照与逐城证据，补充到相同队列；本轮已接入的全量来源仅为上述中英文 Wikivoyage 与 Wikidata，不宣称已穷尽各国旅游局名录。

## 照片与归档要求

优先 Commons 等具备可复用依据的真实图片，明确保存作者、许可、源文件名和来源页面。不能将百科首图自动当作正确景点照：首图可能是地图、平面图或拍于其他国家的同类活动。初始两城额外建立了24条明确照片覆盖，修正王宫平面图、市场地图、错误国家制陶照片等候选。

`exact-place`、`nearby`、`related-theme` 必须按实际匹配程度标注；相关主题照片的上下文要说明拍摄对象和限制。新批次70个条目和2张城市封面均为本地真实图片，未使用 AI 图；少数没有找到具体地点照片的项目使用明确标注的真实区域/主题图片，仍是后续精确替换的目标。酒店环境图不冒充酒店客房。

图片缩略图及压缩操作只能影响派生文件。原始字节和许可记录由资产归档命令另行保存；无法恢复历史原件时应报告缺口，不能把网页缩略图宣称为原件。
